B1

TypeScript Foundation

Complete

Get the whole backend running through a real TypeScript toolchain without a rewrite.

What

Installed typescript, tsx, ts-jest, and matching @types packages — pinned to the versions actually in use (Express 4, Jest 29), not whatever the latest majors happened to resolve to. Added tsconfig.json with allowJs so old .js and new .ts modules keep require()-ing each other freely. Converted the three most load-bearing files — config/environment.js, config/database.js, server.js — to typed .ts.

Why

Every later phase needs a working TS pipeline underneath it — Zod schemas, Drizzle's typed query builder, better-auth's typed session all assume it. Doing this file-by-file with allowJs as a bridge means the other 40+ .js files keep working untouched until their own turn comes.

How

allowJs: true + checkJs: false lets tsc compile mixed .js/.ts in one pass; strict: true only actually bites on the files written in TS. tsx replaces ts-node for dev — instant, zero config. ts-jest transforms just *.ts in Jest, so all six existing test suites needed no changes at all.

Found in the process services/ai/recommendationShortlistService.js had normalizeCoursePayload = (…) with no const — silently relying on Node's sloppy-mode global leakage. Harmless under plain node, but tsc's strict-mode output turned it into a crash. One-word fix.
Example
$ npm run dev      # tsx server.ts — instant, no compile step
$ npm run build    # tsc → dist/
$ npm start        # node dist/server.js
Deliverables

tsconfig.json, jest.config.js, 3 converted files, updated npm scripts (dev, build, typecheck, start).

Completion
  • npm run typecheck clean
  • npm run build produces a working dist/
  • All 15 existing tests still pass
  • npx tsx server.ts and node dist/server.js both boot and connect to the real local Postgres
B2

Zod Validation

Complete

One schema per request shape, enforced at the edge — replacing express-validator and the hand-rolled checks duplicated inside controllers.

What

Zod schemas for register, login, profile update, password change, onboarding/complete, forgot/verify-otp/reset, and — new coverage, not migration — course search & scrape, wishlist/enroll/verify/complete, certificate presign, and the public course catalog list, none of which had any validation before. A single middleware/validate.ts factory. middleware/validation.js (express-validator) deleted entirely; authController.js's and passwordResetController.js's redundant manual checks removed now that their schemas cover the same ground.

Why

The Statement of Work names this exactly: “Zod-based request validation.” It also fixed a real duplication — authController.register was re-validating fields express-validator already checked.

How

All 6 route files converted to .ts, each wiring validate(schema) ahead of its controller. z.coerce.number() handles query-string numbers (page, pageSize, ratings) so controllers no longer hand-roll parseInt/parseFloat on unchecked input.

Found in the process utilities/helpers/helper.js's sendError silently dropped its 4th argument — every validation failure in the whole API returned just “Validation failed” with the specific field errors computed and then thrown away. Fixed so callers actually see which field failed and why. Also fixed 3 live ReferenceError typos in passwordResetController.js (e.message, genericMsg, left — none of those variables existed) that were crashing the OTP-expired and attempts-remaining error paths.
Example
$ curl -X POST /api/auth/register -d '{"email":"bad","password":"123"}'
{"status":"error","message":"Validation failed","data":[
  {"field":"email","message":"Please provide a valid email address"},
  {"field":"password","message":"Password must be at least 6 characters long"}
]}
Deliverables

zod dependency, middleware/validate.ts, 6 schema modules under schemas/, all 6 route files converted to .ts, express-validator removed from package.json, 2 bug fixes.

Completion
  • Every route across all 6 route files rejects malformed input with one consistent 422 shape, field errors included
  • express-validator gone from dependencies
  • Typecheck, build, and all 15 tests pass; verified live against the running server with curl, not just unit tests
B3

Drizzle Migration

Complete

Replaced Sequelize's 9 models with typed Drizzle schema and queries, model by model, against the same tables — including the migration runner itself.

What

db/schema.ts mirrors all 9 tables column-for-column, verified against the live database's information_schema, not just the old Sequelize model files. Conversion ran in the planned order — PasswordReset/OAuthSession/UserIdentity, then User (every auth path), then Course/Review, then the join-heavy trio UserCourse/Certificate/UserRecommendation — plus the two hand-tuned trigram search services and the recommendation worker. scripts/migrate.js and the baseline migration itself were also rewritten off Sequelize's QueryInterface onto plain pg, so sequelize is a fully removable dependency, not just unused in the request path.

Why

The SOW requires this “with a controlled migration path” — which this codebase already half-expected, having moved off sequelize.sync() months ago for exactly this reason.

How

Confirmed against the live DB (not assumed) that id/createdAt/updatedAt have no server-side default anywhere — Sequelize generated all three in JS before every insert. db/helpers.ts's newId()/withTimestamps()/touch() replicate that exactly. The two raw-SQL trigram search services were rebuilt on Drizzle's sql tag (auto-parameterized, same protection as Sequelize's named replacements) instead of hand-escaped string concatenation.

Found in the process A real, serious bug: sanitizeUser() checked for user.toObject (a Mongoose method) instead of Sequelize's toJSON() — meaning every register/login/profile response had been leaking the bcrypt password hash and raw ORM internals in production. Fixed and verified live. Also fixed: a typo'd 'leve' in the global search's allowed-fields set silently made level un-selectable, two dead filters (tags/subjectAreas) referencing columns that don't exist, and confirmed an orphaned, code-referenced-nowhere ScrapeRuns table sitting in the live DB — left untouched, flagged for a human decision.
Example
// Sequelize
User.findOne({ where: { email } })

// Drizzle
db.select().from(users).where(eq(users.email, email))
Deliverables

db/schema.ts, db/client.ts, db/helpers.ts, drizzle.config.ts, all 9 models converted and deleted, migration runner rewritten on plain pg, sequelize + pg-hstore removed, 1 security bug + 2 correctness bugs fixed.

Completion
  • Typecheck, build, and all 15 tests pass on Drizzle
  • Zero require('sequelize') or require(*/models/*) left anywhere in the codebase
  • Verified live against the running compiled build (not just tsx/dev): register → login, wishlist → enroll → verify → complete → certificate, dashboard join, global search, user-course search, and recommendation scheduling all confirmed against the real local Postgres
B4

better-auth Integration

Partial — core done

Email/password auth, sessions, and password reset are on better-auth and verified live. Google/LinkedIn social login is deliberately deferred.

What

better-auth configured with its Drizzle adapter (its own user/session/account/verification tables, linked to our existing Users profile table by a shared id). middleware/auth.js, authController.js (register/login/logout/change-password/profile), and passwordResetController.js's final reset step are fully converted and verified live. socialAuthController.js is untouched — Google/LinkedIn login still issues the old JWT, a deliberate, explicit decision to defer, not an oversight.

Why

Named directly in the SOW. Closes a real gap the audit found: the old JWT was a single 7-day bearer token that could never be revoked. better-auth's session table fixes this — verified by logging out and confirming the exact same token is then rejected.

How

better-auth (and its jose dependency) turned out to be ESM-only — confirmed directly, not assumed: require('better-auth') throws ERR_REQUIRE_ESM in this project. Converting the whole CommonJS backend to ESM was avoided entirely; auth/config.ts instead loads it via a lazy await import(), which CommonJS supports natively. The CLI schema generator (@better-auth/cli / auth@latest generate) has its own unrelated internal bug in this environment, so the exact 4-table schema was pulled by calling getAuthTables() from better-auth/db directly and verified against a real signup's generated SQL.

Found in the process better-auth's Drizzle adapter expects the id column to have a database-level DEFAULT (it omits id from its own INSERTs and lets Postgres generate it) — the first migration attempt had no default and failed with a NOT NULL violation on a live signup. Fixed by adding DEFAULT gen_random_uuid() to all 4 new tables (Postgres 17 has this built in, no extension needed) after dropping and recreating the still-empty tables.
Example
$ curl -X POST /api/auth/logout -H "Authorization: Bearer $TOKEN"
{"status":"success","message":"Logged out successfully"}

$ curl /api/auth/profile -H "Authorization: Bearer $TOKEN"  # same token, right after
{"status":"error","message":"Access token is required"}  # ← the gap that didn't exist before B4
Deliverables

auth/config.ts, 4 new tables + migration, scripts/backfillBetterAuthUsers.js (10 pre-existing users migrated with zero forced password reset), middleware/auth.js + authController.js + password-reset's final step converted, new /api/auth/logout endpoint.

Completion
  • Existing users can still log in with their original password (verified against a real pre-B4 account, not a fresh one)
  • Register → login → profile, change-password, and the full OTP reset → login round-trip all verified live
  • Logout actually revokes the session — the same token is rejected immediately after
Deferred, not done Google/LinkedIn social login still issues the old JWT. Revisit once real Google/LinkedIn OAuth app credentials are available for testing — the redirect-based flow can't be verified with curl the way everything else here was. jsonwebtoken and generateToken/verifyToken stay in the codebase until that's done.
B5

Organizations, Departments & Tenant RBAC

Planned

The one phase that's pure greenfield — nothing here migrates existing logic, because no tenancy concept exists in this codebase today.

What

New tables: organizations, departments, org_members (userId + orgId + departmentId + org-scoped role), invitations (token, email, orgId, role, expiresAt). An invite → accept → org_member flow. Tenant-scoping middleware that derives the caller's org from their membership and injects it into every query. Org-scoped roles — owner/admin/hr/member — layered on top of, not replacing, the existing global role enum.

Why

The audit found zero organization/department/membership concept anywhere in the models, migrations, or routes — exactly the gap behind the frontend's Employer Dashboard, Team, and Assessments views still running on mock data. It's also the SOW's named pre-pilot gate: “Run a tenant-isolation security test pass before pilot sign-off.”

How

Builds directly on B3's Drizzle schema and B4's better-auth session — org membership becomes part of the authenticated session itself, not a bolt-on lookup on every request.

Example

An HR user in Org A hitting a team-roster endpoint must never see Org B's members, even with a fully valid session token — this is the actual test that gates the phase.

Deliverables

4 new tables plus migration, invitation email flow, tenant-scoping middleware, org-scoped RBAC.

Completion
  • Two-org isolation test passes
  • Invitation flow works end to end
  • Every existing protected route is confirmed org-scoped, not just the new ones

Security, Logging, Testing & CI

Planned

The hardening pass — most of it fixes things the audit already found, rather than adding new surface.

What

Rate limiting on auth routes. Structured JSON logs, replacing morgan's plain-text access log. OpenAPI generation straight from B2's Zod schemas. A real integration test suite that hits Postgres instead of mocking it — today's 15 tests are 100% mocked, zero DB-backed coverage. A CI pipeline running typecheck → build → test on every push.

Two audit bugs fixed here The AWS_ACCESS_KEY_ID / AWS_ACCESS_KEY naming mismatch across s3Service.js and the email helper, and the /api/auth/test-ses diagnostic endpoint left live in production auth routes.
Why

SOW sections I (Security, Privacy & Compliance) and J (Testing, CI & Quality) — the parts not already covered by B5's tenant-isolation test.

How

zod-to-openapi turns B2's schemas into a spec with no separate document to maintain. CI targets GitLab CI, matching the repo's actual remote (gitlab.com/adapted/adapted-backend) — not a generic default.

Deliverables

Rate limiting, JSON logging, OpenAPI spec, DB-backed integration tests, .gitlab-ci.yml, both audit bugs fixed.

Completion
